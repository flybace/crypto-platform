# 单文件规模与拆分规则

## 1. 目的

本规则用于保持 Crypto Multi-Market Quant Platform 的代码、合同、测试和文档可阅读、可审查、可维护。文件规模是工程门禁的一部分，不以“先写进去、以后再拆”为默认流程。

## 2. 硬性上限

- 项目内每个可维护的文本文件最多 3000 行。
- 3000 行是硬上限，不允许以注释、空行或生成后再提交的方式绕过。
- 源码、合同、测试、配置、脚本和 Markdown 文档都适用。
- 二进制文件没有稳定的行数语义；二进制资产必须按仓库资产规则管理，不能把二进制改名为文本来规避审查。
- `.git`、依赖安装目录和运行时数据目录不属于项目可维护文件，不纳入扫描；它们也不应提交到 Git。

## 3. 提前拆分阈值

- 文件达到 2400 行时标记为需要拆分的预警状态。
- 文件达到 2700 行时，新增功能必须先完成拆分，不得继续堆叠职责。
- 文件超过 3000 行时，检查脚本必须失败，提交和构建门禁不得放行。

预警不是失败，但必须在同一变更或紧邻变更中记录拆分安排。对于高变更频率的核心模块，建议在 1800 至 2400 行之间主动拆分。

## 4. 拆分原则

拆分应按职责、依赖方向和变更边界进行：

1. 一个文件围绕一个主要职责组织，不按固定行数机械截断类或函数。
2. 领域模型、用例编排、端口、交易所适配器、风险规则和 Web 层分别放置。
3. 不同交易所的差异放在各自的 Venue Adapter，不把所有交易所条件堆进一个文件。
4. 版本化合同按领域和版本拆分，变更一个合同不应迫使无关合同一起修改。
5. 测试按场景和风险边界拆分；Fake Exchange、回放、合同和集成测试不合并成一个巨型测试文件。
6. 文档按计划章节和决策主题拆分；长篇计划不应成为实现细节的唯一存放处。
7. 拆分后通过小型公共接口连接模块，避免复制代码或形成循环依赖。

## 5. 目录约定

```text
contracts/                  版本化领域、执行、GACE 和 AI 合同
src/domain/                 与平台无关的领域模型和规则
src/application/            用例和应用服务
src/ports/                  外部能力端口
src/adapters/venues/        交易所连接器
src/adapters/standalone/    独立运行适配器
src/adapters/gace/          GACE App 适配器
src/services/               跨模块编排服务
src/web/                    HTTP、WebSocket 和接口层
tests/                      按测试层级和故障场景拆分
scripts/                    可重复执行的工程检查脚本
```

## 6. 自动检查

运行：

```powershell
pwsh -File .\scripts\check-file-line-limit.ps1
```

检查脚本默认以项目根目录为扫描根，跳过 `.git`、依赖、构建产物和运行时数据目录，检查其余可维护文本文件，并报告预警和超限文件。退出码为 `0` 才表示通过；出现任何超过 3000 行的文件时退出码为 `1`。

## 7. 变更验收

新增模块时必须同时满足：

- 目录归属符合本规则；
- 文件未超过 3000 行；
- 接近 2400 行时已评估拆分；
- 相关合同、测试和文档没有因为拆分而失去可追溯性；
- 检查脚本在本地和 CI 中均通过。

本规则只约束文件组织和可维护性，不代表目录中的占位文件已经实现任何业务功能。
